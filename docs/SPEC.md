## 0. このアプリが解く問題

「その場面になったら英語が口から出る」状態を作ること。それだけを目的にする。

理解でも語彙でもなく**自動化**が目的なので、必要なのは反復である。ただし反復を支える道具として既存のものは弱い。紙とペンでの100回音読が続かない理由は「飽きる」ではなく、次の3つだと考えている。

第一に、回数を数える行為が音読のリズムを切る。第二に、同じやり方で反復すると40回目あたりで意識が飛び、口は動いているのに何も入らなくなる。第三に、上達が数字で見えないため、続ける根拠が精神論しか残らない。

このアプリはこの3点だけを解く。**回数はマイクの音量検知で自動的に数える。反復は6段階に分けて負荷を自動的に上げていく。上達は「言い始めるまでの秒数」で測る。**

### 0.1 最重要の設計方針：回数は目標ではない

**「100/100」のような達成バーは置かない。** 置いた瞬間に「100回やること」が目的にすり替わり、雑な100回が生まれる。

回数は積算メーターとして淡々と表示するだけにする（「この文 47回 / この会話 12周」）。**卒業判定はレイテンシで行う**。結果として合計回数は100回前後に落ち着くが、それは副産物であって目標ではない。

## 1. 中核メカニズム

### 1.1 6ステージ

台本1本に対して、以下の6段階を順に進む。ステージが上がるほど手がかりが減り、負荷が上がる。

| # | 名前 | 画面表示 | 音声 | 行の順序 | 対象の行 | 最低回数 |
|---|---|---|---|---|---|---|
| S1 | 聞いてなぞる | 英文＋和訳 | お手本再生 | 順 | 全役 | 3 |
| S2 | 重ねて読む | 英文 | 同時再生 | 順 | 全役 | 10 |
| S3 | 見て読む | 英文 | なし（目標時間バー） | 順 | 全役 | 15 |
| S4 | 影を追う | なし | お手本再生 | 順 | 全役 | 15 |
| S5 | 和訳から出す | 和訳のみ | なし | **シャッフル** | 自分の役 | 10 |
| S6 | 相手に返す | なし | 相手の台詞のみ | **シャッフル** | 自分の役 | 10 |

最低回数の合計は63。実際には各段階で足踏みするので合計100回前後になる。

**S1〜S4は両役を音読し、S5〜S6は自分の役だけを扱う。** 前半で表現のストックを増やし、後半で実戦形式に絞る。

**役交代**: S6を終えたトピックは、`myRole` を切り替えてもう一周できる。相手役の台詞は既にS1〜S4で何十回も音読しているので、2周目は驚くほど速く仕上がる。片方の役が終わった時点で「相手の役でもやりますか」を出す。1本の台本から実質2本ぶんの練習が取れるので、費用対効果が高い。役ごとの進捗は `TopicProgress.byRole` に分けて持つ。

### 1.2 進級条件

各ステージには「最低回数」と「達成条件」があり、両方を満たすと次に進める。ただし**進級は強制しない**。条件を満たすと画面に「S4に進めます」と控えめに出るだけで、押さなければ同じステージを何回でも続けられる。回数は積み上がり続ける。

| # | 達成条件 |
|---|---|
| S1 | なし（3回聞けば進める） |
| S2 | 発話率60%以上を3回連続 |
| S3 | 目標時間内に詰まりなく読み切るのを3回連続 |
| S4 | 発話率60%以上を3回連続 |
| S5 | **全行が定着基準を満たす**（§1.4） |
| S6 | **全行が定着基準を満たす** |

S3の目標時間は、お手本音声の実測長 × 係数。係数は回数に応じて 1.3 → 1.15 → 1.0 → 0.9 と自動的に縮む。画面には残り時間バーが横に走り、その中で読み切る。**S3で速度を上げるのは、考える余地を奪って自動化を促すため**であり、速く読むこと自体が目的ではない。

### 1.3 順序シャッフル（後半必須）

会話を頭から通しでやり続けると、文脈と順番で次の台詞を思い出せてしまう。それは定着に見えて定着ではなく、実際の会話では出てこない。

したがって **S5とS6では行の順序を必ずシャッフルする**。定着判定もシャッフル状態での測定でのみ行う。ここを甘くすると「このアプリの中でだけできる人」になる。

シャッフルは完全ランダムではなく、直前に出た行が連続しないようにする程度の制約を入れる。

### 1.4 定着判定

反射的に出るかどうかは回数では測れないが、**言い始めるまでの秒数**でなら測れる。音量検知を実装する以上、これは追加コストゼロで取れる。

```
閾値(ms) = 1200 + 語数 × 60
  → 10語の文なら 1800ms、15語なら 2100ms

定着条件（すべて満たすこと）:
  ・直近3回のレイテンシがすべて閾値未満
  ・その3回に詰まり（発話開始後の1.5秒以上の無音）がない
  ・シャッフル状態（S5以降）での測定である
```

**定着は崩れる。** 定着から7日経過した行は「再確認」対象になり、次のセッションで優先的に出題される。再確認で基準を割ったら定着を外す。これが実質的に間隔反復として機能するので、別途SRSを実装する必要はない。

### 1.5 長い台本はブロックに分ける

実際の場面を自然に書くと、台本は20行を超えることが多い。空港でSIMカードを買う会話を書いてみると11往復・22行になり、1周およそ110秒かかった。これを100回まわすと約180分で、定着ループとしては重すぎる。

そこで**台本を4〜6行のブロックに分割し、ブロック単位で定着させてから通しに移る**。段落ごとに仕上げてから全体を通すのは只管朗読の実践でも一般的なやり方で、記憶の負荷としても妥当になる。

```js
"blocks": [
  { "id": "b1", "label": "用件を伝える",   "from": "ln_001", "to": "ln_006" },
  { "id": "b2", "label": "プランを確認する", "from": "ln_007", "to": "ln_012" },
  { "id": "b3", "label": "開通してもらう",   "from": "ln_013", "to": "ln_018" },
  { "id": "b4", "label": "支払って締める",   "from": "ln_019", "to": "ln_022" }
]
```

**分割ルール**: `blocks` が指定されていればそれに従う。未指定で12行以下ならブロック分割しない（1トピック＝1ブロック扱い）。未指定で13行以上なら、**話題の切れ目を推定せず、単純に5行ずつ機械的に分割する**（推定を入れると外したときに直しづらい。均等分割なら編集画面でドラッグして直せば済む）。

**進行の仕組み**: ブロックごとにステージが独立して進む。b1がS6まで到達したらb2に移る。全ブロックがS6を終えると**通しモード**が解放され、台本全体を通してS5・S6を回す。ホームには「b2 / 4ブロック中」と表示する。

ブロック分割は行数が多いときの救済策なので、**12行前後の台本ならブロックを意識せずに使える**ようにする。UIにブロックの概念が出てくるのは13行以上のときだけにする。

### 1.6 語彙の予習と復習（S0 と 語彙モード）

文単位の反復だけでは復習の粒度が粗すぎる。知らない語が混じったまま音読に入ると、意味が乗らないまま口だけ動く時間が生まれるし、あとから「あの表現なんだっけ」と思い出したいときに文章まるごと回すしかなくなる。**語彙を独立した層として持たせる。**

**S0 下ごしらえ（S1の前）**

トピックを始める前に、その台本に出てくる語・表現を一巡する。まず英→和で意味を入れ（各1回、タップで進む）、次に和→英で口に出す（各3回）。ここで語が入っていると、S1以降の音読で意味が乗る。所要は20語で3分程度。

**語彙復習モード（いつでも単独で使える）**

トピックを横断して、語だけを回すモード。判定は文とまったく同じ仕組みを使う。**和訳を出して、言い始めるまでのレイテンシを音量検知で測る。**

```
語の定着閾値(ms) = 900 + 語数 × 60
  → 単語1語なら 960ms、"run out of"（3語）なら 1080ms
```

文より短く設定する。語は文脈を組み立てる必要がないので、反射はもっと速くていい。

**文脈から切り離さない**

語彙カードには必ず**その語が出てくる行**を紐づける（`lineIds`）。復習画面で「この語が出る文を聞く」を1タップで再生できるようにする。単語帳として孤立させると、覚えた気になるだけで会話では出てこない。

**再確認への合流**

ホームの「再確認が必要」には、文と語を混ぜて出す。ユーザーから見れば同じ1つの復習キューで、中身が文だったり語だったりするだけ。別々のキューにすると片方が放置される。

**Ankiへの書き出し**

既にAnkiを使っているので、深追いはしない。語彙カードを `表\t裏\tタグ` のTSVで書き出すボタンを置く。アプリ内の語彙復習は「そのトピックをやっている期間の集中復習」、Ankiは「長期の保守」と役割を分ける。

### 1.7 声が出せない時間のための「書くレーン」

音読ステージは声を出せることが前提になっている。しかし現実には**声を出せない時間のほうが長い**。電車の中、診療の合間、家族が寝たあと。その時間を捨てると1日10分の習慣が週2回に落ちる。

そこで同じ台本に対して、声を使わない2つのドリルを並走させる。**音読レーンの代替ではなく、同じ台本を別の入り口から叩くもの**として位置づける。進捗は同じ `Progress` に書き込まれ、どちらで回しても累計回数は積み上がる。

| レーン | 中身 | 使う場面 |
|---|---|---|
| 音読レーン | S1〜S6（§1.1） | 声が出せるとき。これが本体 |
| 書くレーン | 和文英訳ドリル / ディクテーションドリル（§9） | 電車、待ち時間、深夜 |

書くレーンは定着判定には使わない。**反射はキーボードでは測れない**（打鍵速度が混ざる）。書くレーンは正答率だけを記録し、定着の認定は音読レーンのレイテンシでのみ行う。ただし書くレーンで詰まった行は音読レーンでも優先的に出題される。

ホームには常に両方の入口を出し、**「今は声を出せますか」を最初に1回だけ聞く**。答えに応じて出す導線を変える。毎回聞くと鬱陶しいので、セッション開始時の1タップだけにする。

### 1.8 分解して叩く（チャンク層と積み上げドリル）

語の層と文の層だけでは粒度に穴がある。**文が言えないとき、その文のどこで落ちているかが分からない**まま100回叩くことになる。長い文ほどこれが起きる。

そこで語と文の間に**チャンク層**を置く。粒度は3段階になる。

```
語        run out of
チャンク   before I leave / if I run out of data
文        What happens if I run out of data before I leave?
会話      （通し周回）
```

**チャンクは独立した復習単位にはしない。** 復習キューにチャンクまで混ぜると細かすぎて管理が破綻する。チャンクは「詰まった文を分解するための道具」として位置づける。

**積み上げドリル（後ろから）**

詰まりが続く文に対して発動する。文末から順に足していく。

```
Could you place it on the scale for me?

  1回目   for me
  2回目   on the scale for me
  3回目   place it on the scale for me
  4回目   Could you place it on the scale for me?
```

**後ろから積むのは、文末の抑揚とリズムが最後まで壊れないため。** 前から積むと毎回イントネーションを作り直すことになり、音として定着しない。これは英語教育で長く使われている手順で、素直に踏襲する。

**発動条件**: S3またはS5で同じ行に3回連続で詰まりが出たら、「分解して練習しますか」を出す。押せば積み上げドリルに入り、終わったら元のステージに戻る。**自動で強制発動はしない**（流れを切られると萎える）。トピック詳細から手動で任意の行を分解することもできる。

**チャンクの自動分割**

```
切る位置:
  ・カンマの直後
  ・前置詞の直前（in, on, at, for, with, about, from, to ...）
  ・接続詞の直前（and, but, so, because, if, when, that ...）
  ・to不定詞の直前
  ・関係詞の直前（who, which, that ...）

調整:
  ・結果が1語だけになったら前のチャンクに吸収する
  ・5語を超えたら、その中の最も強い切れ目でもう一度割る
  ・目標は2〜4語のかたまり
```

自動分割は必ず外すので、**プレビュー画面と積み上げドリル内でチャンク境界をタップして動かせる**ようにする。境界の編集は `Line.chunks` に保存され、次回以降そのまま使われる。

**詰まり位置の推定**

音読中の詰まり（§2.5）が文のどのあたりで起きたかを、発話開始からの経過時間とチャンクの累積想定時間から推定する。厳密ではないが「前半／中盤／後半」程度の粒度は取れる。これを積み上げドリルの開始位置に使う（後半で詰まっているなら文末2チャンクから始める）。

**よく詰まるチャンクの集計**

トピックをまたいで「詰まりが多いチャンク」を集計し、設定画面に上位を出す。`if I run out of` のような特定の構文で毎回止まっていることに気づける。ここは語彙リストに手動で昇格させられるようにする。

### 1.9 上達の可視化

トピックごとに「定着した行 8/12」を表示する。加えて**レイテンシの推移グラフ**を1本だけ置く。横軸が累計回数、縦軸が平均レイテンシ。10回目に4.2秒、60回目に1.8秒、100回目に0.9秒、という曲線が見えれば、反復に意味があったことが数字で確認できる。

グラフはこれ1つだけにする。統計を増やすとアプリを見る時間が増えて音読する時間が減る。

## 2. 音量検知エンジン（このアプリの心臓部）

音声認識は使わない。**音量（RMS）だけを見る。** ネット不要、軽量、発音の良し悪しに左右されない、プライバシー上も安全。

### 2.1 初期化と較正

```js
navigator.mediaDevices.getUserMedia({
  audio: {
    echoCancellation: true,    // TTSの回り込みを抑える
    noiseSuppression: true,
    autoGainControl: false     // ← 必ず false。自動ゲインだと閾値が動いてしまう
  }
})
→ AudioContext → MediaStreamSource → AnalyserNode
   fftSize = 2048, smoothingTimeConstant = 0.3
```

**較正**: セッション開始時に「1.5秒間、静かにしてください」と出してノイズフロアを測る。

```js
onsetThreshold  = Math.max(noiseFloor * 3.5, 0.008)  // 発話開始の閾値
offsetThreshold = onsetThreshold * 0.7               // 発話終了の閾値（ヒステリシス）
```

開始と終了で閾値を変えるのが重要。同じ値にするとチャタリングして発話区間が細切れになる。

較正値は端末とマイクごとにほぼ一定なので、設定に保存して次回以降は再利用する。ただし「うまく検知されない」ときに1タップで再較正できるボタンを、練習画面に常時置く。

**測った値が異常なら採用しない。** `noiseFloor` が 0.05 を超えたら、うるさい場所にいるか較正中に声が入っている。そのまま採用すると閾値が上がりすぎて**何を喋っても検知されない**状態になり、原因も分からない。1回だけ自動でやり直し、それでも高ければ既定値を使って「静かな場所で較正し直してください」を1行出す。

### 2.2 発話検知ループ

```js
// 20ms間隔（setInterval または requestAnimationFrame）
getByteTimeDomainData(buf)
rms = sqrt(Σ((buf[i]-128)/128)² / N)

未発話中: rms > onsetThreshold が 3フレーム連続 → 発話開始(onset)
発話中:   rms < offsetThreshold が 15フレーム連続(=300ms) → 発話終了(offset)
```

無声子音で始まる文（Sure, Thank you, Could I）は立ち上がりが弱いので、閾値は低めに倒す。誤検知は後述の取り消しで救う。

**「1回」がどこで終わるかを決めておく。**

```
offset から 2500ms 新しい onset が来なければ、その「1回」を確定する
```

確定した時点で §2.3 の判定にかける。**1回の中に無音を挟んだ複数の発話区間が入りうる**ので、`spokenMs` はその合計になる。§2.5 の詰まり（1500ms）は1回の内側で起きる出来事で、2500msまで延びたらその回は終わったものとして閉じる。

この2つの値が近すぎると詰まった瞬間に回が切れ、離れすぎると次の回の先頭を前の回に飲み込む。**実機で必ず調整する**ので定数にまとめること。

### 2.3 1回のカウント判定

```
expectedMs = そのラインのお手本音声の実測長（一度でも再生していれば）
             無ければ 語数 × 400ms ÷ rate で代用する
spokenMs   = その回の発話区間の合計

spokenMs / expectedMs >= 0.55  → 1回としてカウント成立
```

**実測値があるなら内蔵TTSでもそれを使う。** 同じ `rate` でも端末とボイスによって実際の長さは変わるので、語数から出した概算より実測のほうが必ず正確になる。語数式はまだ一度も再生していない行のための代用にすぎない。

実測値は測ったときの `rate` と一緒に保存し、あとで速度を変えたら `実測Ms × 測定時のrate ÷ 新しいrate` で補正する。再生し直すまで待たない。

0.55は緩めに設定してある。読む速さには個人差があり、厳しくすると「ちゃんと読んだのにカウントされない」が起きる。これが起きると人は手動タップに戻ってしまう。**閾値は定数として先頭にまとめ、設定画面からも変更できるようにする。**

### 2.4 レイテンシ測定

```
キュー表示 t0 → 最初の onset t1 → latency = t1 - t0
```

記録には**直近5回の中央値**を使う。平均だと咳や物音の外れ値に引っ張られる。

誤検知対策として、練習画面に「今のはナシ」ボタンを常時置き、直前の1回の記録（カウントとレイテンシの両方）を取り消せるようにする。**取り消しが1タップでできることが、自動カウントを信用してもらう条件**になる。

**onset が来ないまま終わる場合を必ず持つ。** キュー表示から10秒待って一度も発話が無ければ、その回を「発話なし」として閉じる。レイテンシは記録せず、カウントもしない。**無限に待つと画面が固まったように見える。**

このとき出す文言は「聞こえませんでした」ではなく、もう一度促す形にする。言えなかったこと自体は失敗ではないし、責められると続かない。

### 2.5 詰まりの検知

発話開始後、1.5秒以上の無音が入ったら「詰まり」としてその回に記録する。回数を重ねると詰まりが消えていくのが見え、定着判定の条件にもなる。

### 2.6 TTSの音を拾う問題

`echoCancellation: true` で大半は抑えられる。加えてステージごとに扱いを変える。

S2（重ねて読む）はTTSと同時に発声するので、多少拾っても声を出している事実は変わらず問題にならない。S3・S5はTTSが鳴らないので無関係。S1・S4・S6ではTTS再生中はカウント窓を閉じる（S6は相手の台詞が終わってから測定を開始する）。

初回起動時に一度だけ「イヤホンの使用を推奨します」と案内する。

### 2.7 タップモードへのフォールバック

マイクが使えない環境（`file://` での起動、マイク不許可、電車内で声が出せない）のために、タップで1回を記録するモードを必ず持つ。**音量検知が使えないときにエラーを出すのではなく、黙ってタップモードに切り替えて理由を1行添える。**

一度マイクを拒否するとブラウザが記憶するので、**アプリ側からは二度と許可を求められない。** 設定画面に「マイクを使えるようにする手順」を置き、ブラウザの設定から許可し直す方法を1画面で示す。ここが無いと、間違って拒否した時点でこのアプリの中核機能が永久に失われる。

### 2.8 モジュールの境界

`EST.mic` はUIから完全に独立させ、**コンソールから単体で動かせる形**にする。ここを守らないと、実機での閾値調整のたびに練習画面を経由することになって手が付けられなくなる。

```js
EST.mic.start() / stop()
EST.mic.calibrate()          // → Promise<{noiseFloor, onsetThreshold}>
EST.mic.gate(open)           // TTS再生中は閉じる（§2.6）
EST.mic.markCue()            // レイテンシの t0 を打つ（§2.4）
EST.mic.cancelLast()         // 「今のはナシ」（§2.4）
EST.mic.on(event, cb)        // onset / offset / level / rep / stall / timeout
```

`rep` が**「1回ぶんの発話が確定した」**イベントで、`{ spokenMs, latencyMs, stalls, segments }` を渡す。

**`markCue()` が呼ばれていなくても `rep` は出す。** その場合 `latencyMs` は `null` にする。キューを打たずに喋り始めても発話の事実は変わらないし、**コンソールから `start()` して喋るだけで動作を確認できる**ようにしておかないと、実機での閾値調整のたびにキューを打つ手間が増える。§2.8 の狙いはそこにある。

**カウント成否の判定（§2.3）はここでは行わない。** 何回と数えるかはステージ側（F5）の仕事で、`EST.mic` は起きた事実だけを報告する。`expectedMs` を知っているのはステージ層なので、そこに判定を置くほうが素直でもある。**この線引きを崩すと、マイクモジュールが台本を知らないと試験できなくなる。**

## 3. 練習画面（最も重要なUI）

音読中の画面は極限まで削る。情報が多いと画面を見てしまい、音読がおろそかになる。

```
┌─────────────────────────┐
│  S3 見て読む      18回   │  ← 小さく。ステージ名と、そのステージでの回数
│                          │
│                          │
│   May I see your         │  ← 中央に大きく。ステージに応じた表示
│   passport, please?      │
│                          │
│  ▓▓▓▓▓▓▓░░░░░░           │  ← S3のみ：目標時間バー
│                          │
│  ▁▃▅▇▅▃▁                 │  ← 音量バー（検知されているのが見える）
│                          │
│  この文 47回 / この会話 12周 │  ← 積算メーター。ごく小さく
│  [今のはナシ]  [再較正]    │
└─────────────────────────┘
```

**音量バーは必須。** 「ちゃんと検知されている」が視覚的に分からないと不安になり、手動タップに戻ってしまう。自分の声に反応して動くバーがあるだけで信頼できる。

進行は自動。1行終わったら次の行へ、最終行まで行ったら次の周へ、と止まらずに回り続ける。**ユーザーが押すべきボタンは原則ゼロ**にする。押すのは中断するときだけ。

画面は常時点灯にする（Screen Wake Lock API。非対応環境は諦める）。音読中に画面が消えるのは致命的に萎える。

## 4. 一覧モードと横断検索（思い出す前に確認する）

練習ループとは別に、**確認するための画面**を持つ。「あの言い回し何だっけ」を最短で解決する用途で、これは練習ではなく参照である。

### 4.1 一覧モード

和訳だけを箇条書きで縦に並べ、タップすると英文が下に開く。

```
空港でSIMカードを購入する            [和→英 ⇄]  [全部開く]

・スマホ用のSIMカードが欲しいのですが          🔊  [見る]
・ご滞在はどのくらいですか？                  🔊  [見る]
・帰国前にデータを使い切ったらどうなりますか？    🔊  [見る]
      └ What happens if I run out of data before I leave?
・もう一つだけ。私のスマホで使えますか？        🔊  [見る]
```

トグルで英→和に反転できる。スピーカーは開かなくても音だけ聞ける（音で思い出せるか試せる）。文の一覧と語彙の一覧をタブで切り替える。

**開いた＝思い出せなかった、として記録する。** 開いた行は復習キューに入る。自己申告より正確で、しかもユーザーは余計な操作を一切していない。ただし「答え合わせのために開いただけ」のこともあるので、記録するかどうかは設定で切れるようにする（既定はON）。

### 4.2 横断検索

全トピックを対象に、日本語でも英語でも引ける。「していただけますか」と打つと該当する英文が並ぶ。**検索対象は自分が音読した台本だけ**なので、辞書を引くより速く、しかも必ず自分の文脈の中で出てくる。ここが市販の辞書やアプリにはできない部分になる。

部分一致で十分。カタカナはひらがなに正規化してから比較し、表記揺れを吸収する。ヒットした行からその場で音声再生と、そのトピックの練習への遷移ができる。

### 4.3 書き出し

一覧をテキストまたはMarkdownで書き出せる。紙で持ちたいとき、移動中に眺めたいときのため。語彙一覧はAnki用TSVでも書き出せる（§1.6）。

## 5. データモデル

### 5.1 Topic

```js
{
  "id": "tpc_20260803_a1b2",
  "title": "空港のチェックインカウンター",
  "titleEn": "At the Check-in Counter",
  "level": "B1",
  "tags": ["旅行"],
  "audience": "tamo",                // "tamo" | "mari" | "both"。誰の台本か（§5.9）
  "myRole": "S2",                    // 自分が担当する役。S5/S6で使う
  "speakers": [
    { "id": "S1", "label": "Agent",    "gender": "female" },
    { "id": "S2", "label": "Traveler", "gender": "male" }
  ],
  "blocks": [ /* Block[] — §1.5。13行以上のとき使う。未指定なら自動生成 */ ],
  "lines": [ /* Line[] */ ],
  "words": [ /* Word[] — §5.3 */ ],
  "createdAt": 0, "updatedAt": 0, "schemaVersion": 3
}
```

推奨は10〜14行（1周およそ60秒）だが、**アプリ側で行数を制限しない**。取り込み時に「1周 約◯秒 / ◯ブロック」と表示して判断材料だけ出す。

`audience` は**2人が別々の課題をやるため**の振り分け（§5.9）。未指定なら `"both"` として扱う。

### 5.2 Line

```js
{
  "id": "ln_003",
  "speakerId": "S1",
  "en": "Are you checking any bags today?",
  "ja": "本日、お預けの荷物はございますか？",
  "note": "check a bag = 荷物を預ける",        // 任意
  "alt": ["Do you have any bags to check?"],  // 任意。英作文ドリルの別解（§9.3）
  "chunks": ["Are you checking", "any bags", "today"],  // 任意。未指定なら自動分割（§1.8）
  "skip": false                                // ト書き等
}
```

`alt` と `chunks` は**未指定でよい**。`alt` は英作文ドリルで「これも正解として登録」を押すたびに育っていく（§9.3）。`chunks` はアプリが自動分割し、境界をタップで直した結果が保存される。台本を作る時点で書く必要はない。

v1.1にあった `blanks` `keyPhrases` `linking` は削除する。`blanks` は自動選択に任せ、`keyPhrases` は `words[]` に統合し、`linking` は将来拡張へ送った。

### 5.3 Word（語彙カード）

トピックに紐づく語・表現。`Topic.words[]` として持つ。

```js
{
  "id": "w_007",
  "en": "run out of",
  "ja": "使い切る、切らす",
  "type": "phrase",            // "word" | "phrase"
  "lineIds": ["ln_007"],       // この語が出てくる行。復習時に文を再生するのに使う
  "note": "旅行英語の最頻出表現"  // 任意
}
```

**生成方法は3経路**。①台本JSONに `words[]` が入っていればそれを使う（Claudeに作らせるのが基本。付録A参照）。②未指定なら、各行の `note` に出てくる `X = 意味` のパターンと、ストップワード約60語を除いた低頻度の内容語から自動抽出する。③アプリ内でユーザーが追加・編集・削除できる。

**音読中に語を拾えるようにする。** 練習画面で英文の単語を長押しすると「語彙に追加」が出る。音読していて引っかかった語をその場で拾えないと、結局あとで拾い直さなくなる。

### 5.4 WordProgress（語彙の進捗）

```js
{
  "key": "tpc_xxx::w_007",
  "topicId": "...", "wordId": "...",
  "counts": { "recognize": 4, "produce": 12 },   // 英→和 / 和→英 それぞれの回数
  "latency": { "history": [2100, 1600, 980], "median5": 1600, "best": 980 },
  "mastered": false, "masteredAt": null,
  "updatedAt": 0
}
```

判定ロジックは `Progress` と共通の関数を使う。閾値の係数だけ差し替える（`900 + 語数×60`）。**文と語で別々の判定コードを書かないこと。**

### 5.5 Progress（ラインごと）

```js
{
  "key": "tamo|tpc_xxx|ln_003",     // profileId を前置する（§5.9）
  "profileId": "tamo",
  "topicId": "...", "lineId": "...",
  "counts": { "total": 47, "byStage": {"S1":3,"S2":12,"S3":18,"S4":9,"S5":5,"S6":0} },
  "latency": {
    "history": [4200, 3800, 2900, 2100, 1750],   // 直近20件まで保持
    "median5": 2100,
    "best": 1750
  },
  "stalls": 0,                        // 直近の詰まり回数
  "openedCount": 0,                   // 一覧モードで開いた回数（§4.1）
  "lastOpenedAt": null,
  "mastered": false,
  "masteredAt": null,                 // 定着した日時。7日後に再確認対象
  "updatedAt": 0
}
```

`openedCount` は §4.1 の「開いた＝思い出せなかった」を数えるためのもの。**一覧モードで1行ずつ開いたときだけ増やす。** 「全部開く」は一括で目を通す操作なので数えない。検索は移動のための操作なので、検索したこと自体では増やさない（検索から一覧に入って開けば増える）。

### 5.6 TopicProgress（トピックごと）

```js
{
  "topicId": "...",
  "stage": "S3",                      // 現在のステージ
  "laps": { "total": 12, "byStage": {...} },   // 通し周回の回数
  "sessions": [ {"date":"2026-08-03","laps":10,"minutes":11} ],  // 日次ログ
  "streak": 5,                        // 連続日数
  "latencyTrend": [ {"totalCount":10,"avgMs":4200}, ... ]  // グラフ用
}
```

### 5.7 Settings

```js
{
  "engine": "local",                  // "local" | "cloud"
  "cloud": { "endpoint": "", "token": "", "voiceMap": {}, "model": "tts-1-hd" },
  "ttsRate": 0.85,                    // §7.5 の5段階のいずれかであること
  "localVoiceEn": null,
  "localVoiceByGender": { "female": null, "male": null },   // §7.2 話者別
  "mic": { "noiseFloor": null, "onsetThreshold": null, "calibratedAt": null },
  "countRatio": 0.55,                 // カウント成立の発話率
  "masteryBase": 1200, "masteryPerWord": 60,   // 定着閾値の係数
  "inputMode": "voice",               // "voice" | "tap"
  "dailyGoalLaps": 10,
  "theme": "auto", "fontScale": 1.0
}
```

**`ttsRate` の既定は 0.85 とする。** §7.5 の5段階（0.7 / 0.85 / 1.0 / 1.15 / 1.3）に必ず含まれる値にすること。段階外の値を既定にすると、設定画面を開いただけで速度が黙って変わる。

0.85 を選ぶのは、**使う2人が A1〜A2 の段階にいる**ため。1.0 でシャドーイング（S4）に入ると口が追いつかず、続かない。慣れたら1タップで上げられる。最終的には 1.0 以上で回せる状態を目指す。

### 5.8 ストレージ（IndexedDB `est-db` v3）

| ストア | keyPath | 用途 |
|---|---|---|
| `topics` | `id` | 台本（`lines` と `words` を含む） |
| `progress` | `key` | ラインごとの進捗 |
| `wordProgress` | `key` | 語彙ごとの進捗 |
| `topicProgress` | `topicId` | トピックごとの進捗・ブロック・ステージ・日次ログ |
| `audio` | `key` | 外部TTSの音声キャッシュと、お手本音声の実測長（`dur|...`） |
| `settings` | `k` | 設定（`"app"` 1件） |

**実測長（§2.3）は `audio` ストアに置く。** ストアを増やさずに済むうえ、性質が一致している。どちらも端末とボイスに依存し、消えても再生すれば作り直せる。したがって §6.4 のバックアップ対象にも含めない。

### 5.9 プロフィール（部屋）

**2人とも学習者で、扱う台本もレベルも別。** 同じ仕組みを使って別々の課題をやる。入り口は1つで、起動時に「どちらの部屋か」を選ぶ。

台本を作って配信するのはタモやんだが、それは**実装担当だから**であって、まりの教材係だからではない。タモやんは自分用の台本も作り、自分の部屋で自分の課題をやる。

```js
profileId: "tamo" | "mari"
```

起動時に一度だけ聞き、`localStorage` の `est-profile` に保存する。以降は自動復元し、設定画面から切り替えられる。**別々のスマホで使う前提でも必ず持たせる。** 機種変更や共有端末で必ず要るようになり、後から足すとキー設計の変更を伴って高くつく。

| データ | 分け方 | 理由 |
|---|---|---|
| `topics`（台本） | **`audience` で振り分け** | 2人は別の課題をやる。§5.1 |
| `progress` | プロフィールごと | 周回数も定着も別人格 |
| `wordProgress` | プロフィールごと | 同上 |
| `topicProgress` | プロフィールごと | ステージ・ブロック・日次ログ |
| `settings` | プロフィールごと | 目標周回数・音量閾値・声の設定 |
| `audio` | 共有 | 同じ音声を2度作らない |

キーは既存の先頭に `profileId` を足すだけにする。

```
progress       key     "tamo|tpc_xxx|ln_001"
wordProgress   key     "mari|tpc_xxx|w_003"
topicProgress  topicId "tamo|tpc_xxx"
settings       k       "app|tamo"
```

**進捗はお互いに見えない。同期もしない。** 各自の端末内で完結する。相手の周回数や連続日数は一切表示しない。

**台本の振り分け**

`Topic.audience` で誰の課題かを決める。

| 値 | 見える部屋 | 使いどころ |
|---|---|---|
| `"tamo"` | タモやんのみ | タモやんのレベル・目的に合わせた台本 |
| `"mari"` | まりのみ | まりのレベル・目的に合わせた台本 |
| `"both"` | 両方 | 2人とも必要なもの（旅行前の共通場面など） |

**トピック一覧・検索・復習キューは、自分の部屋に属するものだけを対象にする。** レベルが違う相手の台本が混ざると、一覧が使いものにならなくなる。

**権限**

| | タモやん | まり |
|---|---|---|
| 練習・一覧・検索 | 自分の台本 | 自分の台本 |
| 台本の作成・編集・削除 | ○（両者ぶんを作れる） | **×** |
| `audience` の指定 | ○ | × |
| 配信用の書き出し | ○ | × |
| バックアップ／復元 | 全体 | 自分の進捗のみ |

**まりが編集できないのは実装・配信をタモやんが担うからで、役割の上下ではない。** `mari` プロフィールでは編集系の導線を**非表示にする**（グレーアウトではなく出さない）。誤操作の防止と画面を単純に保つため。

タモやんの編集画面には `audience` の選択（自分用 / まり用 / 両方）を必ず置く。**新規作成時の既定は「自分用」**にする。既定を「両方」にすると、相手の一覧に意図しない台本が流れ込む。

**相手用の台本を編集する経路**

一覧を厳密に絞ると、まり用の台本を保存した瞬間にタモやんの一覧から消えて、二度と編集できなくなる。**タモやんの部屋にだけ絞り込みチップを出して逃げ道を作る。**

```
トピック   [自分用] [まり用] [両方]      ← タモやんの部屋にのみ表示
```

- 既定は「自分用」。つまり `tamo` と `both` が出る、そのまま練習に入れる状態
- **自分の部屋に属さない台本が1件も無いうちはチップ自体を表示しない。** まり用の台本を作るまでホームの見た目は変わらない。ホームは練習に入るための画面で、管理UIを常設しない（§8）
- **自分の部屋に属さない台本をタップしたら、練習ではなく編集画面を開く。** 相手用の台本に自分の進捗レコードが付くのを防ぐ
- まりの部屋にはチップを出さない。常に自分の台本だけ

**`audience` は後から変えられるようにする**

作った直後は判断が付きにくい。**使ってみてから「これはまり向きだった」と気づくほうが普通**なので、振り分けはいつでもやり直せる必要がある。

トピック詳細に切り替えを置く（タモやんの部屋にのみ表示）。編集画面を開き直さずに変えられるようにする。編集画面の中だけに置くと、自分の部屋の台本は詳細画面から編集へ入る手数が増えて、結局やり直さなくなる。

- 変更した瞬間に一覧から消えることがあるので、**変更後は必ず結果を文言で出す**（「まり用にしました。自分の一覧には出ません」）
- **進捗レコードは触らない。** キーが `profileId|topicId|lineId` なので `audience` を変えても各自の周回数と定着は保持される。`tamo` に戻せばそのまま復帰する
- 相手の端末では次の配信取り込み時に一覧から消える／出てくる。進捗は §6.5 の規則どおり残す

## 6. 台本の投入

### 6.1 3つの作成経路

台本は自分で用意する前提なので、作る手段を3つ持たせる。**どの経路でも最終的に同じ編集プレビューに合流し、保存先はアプリ内（IndexedDB）で統一する。**

**経路1: テキストを貼り付ける（主導線）** — 台本らしいテキストをそのまま貼ると、アプリが話者・英文・和訳に分解して構造化する。JSONを触らずに済むので、思いついた場面をすぐ入れられる。

```
Staff: How long are you staying?
ご滞在はどのくらいですか？
You: About ten days.
10日ほどです。
```

以下の形式をすべて同じ結果に解析する。話者ラベルあり／なし、英日交互、区切り文字（タブ / `|` / `｜` / `/`）による列分割、英文ブロックのあとに和文ブロックが続く形（`---` または連続空行2つ以上で区切り、行数一致を条件に対応付ける）、英文のみ。

```
解析手順:
1. 正規化（CRLF→LF、全角スペース→半角、空行の畳み込み）
2. 各行を EN / JA / IGNORE に分類
   日本語文字 [ぁ-んァ-ヶ一-龥ー] の比率 >= 0.15 → JA
3. 行頭の「ラベル:」を話者として抽出
   出現種類が1〜6種なら採用。7種以上なら「コロンが多いだけ」とみなして不採用
   時刻(10:30)とURL(https:)は除外する
4. 区切り文字を含む行が全体の70%以上なら列分割に切り替える
5. EN行の直後の連続するJA行をその訳とみなす
   JA行が2行続いたら結合。EN行が2行続いたら前者は訳なしで確定
6. 話者・ブロック・語彙を自動生成して編集プレビューへ
```

**必ず間違えるので、解析後は編集プレビューを強制的に通す。** 自動解析の精度を上げることより、3タップで直せる編集画面のほうが重要になる。

**経路2: JSON読み込み** — Claudeに台本を作らせてJSONを受け取る（プロンプトは付録A）。`words` や `blocks` まで揃った状態で入るので、腰を据えて教材を作るときはこちらが速い。ファイル選択とテキスト貼り付けの両方に対応する（貼られた文字列がJSONとして解釈できれば経路2、できなければ経路1、と自動で振り分ける）。

**経路3: アプリ内で1行ずつ書く** — 空のトピックを作って、英文・和訳・話者を足していく。既存トピックへの1行追加も同じ画面で行う。

### 6.2 編集プレビュー（全経路の合流点）

各行が「話者セレクト / 英文 / 和訳」の3要素で縦に並ぶ。行の追加・削除・並べ替え・分割・結合ができる。話者ラベルの一括リネーム、`myRole` の選択、ブロック境界のドラッグ移動、語彙リストの追加削除ができる。

上部に **「1周 約◯秒 / ◯行 / ◯ブロック / 語彙◯個」** を常時表示する。ここで長すぎることに気づけるようにする。

### 6.3 取り込み処理

```
1. JSON.parse（失敗時は行番号付きで表示。「不正なJSON」だけ出さない）
2. スキーマ検証。エラーは全部まとめて出す（1個ずつ直させない）
3. id重複 → 上書き / 別トピックとして追加 / 中止 を選ばせる
4. lines[].id が無ければ ln_001 から自動採番
5. myRole 未指定 → 話者選択画面を出す（S5/S6に必須なので飛ばせない）
6. blocks 未指定かつ13行以上 → 5行ずつ機械的に自動分割
7. words 未指定 → note と内容語から自動抽出
8. 編集プレビュー → 保存
```

| 項目 | 必須 | 検証 |
|---|---|---|
| `title` | ○ | 1文字以上 |
| `lines` | ○ | 1件以上 |
| `lines[].en` | ○ | 英字を含む1文字以上 |
| `lines[].ja` | — | 無ければ空。ただしS5が使えなくなる旨を警告 |
| `speakers[].id` | ○ | 重複不可 |
| `myRole` | — | 無ければ取り込み時に選択させる |
| `audience` | △ | **外部JSON**は無ければ `"both"`。**編集画面からの保存は必須**（§5.9） |

**`audience` の「未指定なら `both`」を編集画面に適用しない。** この既定値は外部から来たJSON（配信・取り込み）が古い形式でも壊れないための救済であって、編集画面には要らない。編集画面で未指定のまま保存できてしまうと、**まり用に作ったつもりの台本が黙って `both` になり、相手の一覧に流れ込む。** 値が入っていなければ `myRole` と同じように保存を止める。

誤った値が黙って通るより、保存できずに怒られるほうが安全な項目である。誰に見えるかを決めるフィールドなので、間違いが表に出るまでに時間がかかる。

### 6.4 エクスポートとバックアップ

トピック単体のJSON書き出しと、**全トピック＋全進捗＋設定の全体バックアップ**。個人アプリはデータが飛ぶと二度と使われなくなるので、ここは必ず作る。トピック保存時に全データJSONを自動生成して直近3世代を `settings` 内に保持する。音声キャッシュはバックアップに含めない（再生成できるため）。

復元時は「上書き」か「マージ（同idは新しい方）」を選ばせる。

### 6.5 台本の配信と同期

台本を作るのはタモやんだけ（実装担当だから）。**2人ぶんの台本を1つのJSONに入れて配信し、各端末は自分の部屋の分だけを取り込む。**

```
silmotoki-tech.github.io/Tamoyan-English/
├── index.html          アプリ本体（1枚）
└── data/scripts.json   配信台本。タモやんだけが更新する
```

**取得の流れ**

```
1. 起動時に data/scripts.json を fetch（?t=タイムスタンプ でキャッシュ回避）
2. 取れなければ何もしない。前回取り込んだ内容でそのまま動く
3. 取れたら publishedAt を比較し、新しければ topics を更新
4. audience が自分の部屋に合うものだけを一覧に出す
   （データ自体は全件保存してよい。プロフィール切替で即座に切り替わる）
5. 更新しても進捗は消さない。lineId が一致する行の進捗は引き継ぐ
6. ホームに「台本を更新しました（3件）」を一度だけ出す
```

```js
// 配信JSONの形。2人ぶんを1ファイルに入れる
{
  "publishedAt": 1754179200000,
  "topics": [
    { "id": "tpc_xxx", "audience": "tamo", /* ... */ },
    { "id": "tpc_yyy", "audience": "mari", /* ... */ },
    { "id": "tpc_zzz", "audience": "both", /* ... */ }
  ]
}
```

ファイルを2つに分けない。**分けると片方だけ更新し忘れる**し、`publishedAt` の比較も二重になる。

**進捗を壊さないための規則**

- **`lines[].id` は一度振ったら変えない。** 行を削除しても残りの id を詰め直さない
- 台本を根本から作り直すときは**新しい `topic.id`** にする（別トピック扱いにして進捗を混ぜない）
- 配信から消えたトピックは端末の一覧からも消すが、**進捗レコードは残す**（再配信で復活する）

**タモやんの更新手順**

```
1. アプリ内で台本を追加・編集し、audience を指定する（自分用 / まり用 / 両方）
2. 設定 →「配信用に書き出す」で scripts.json を得る（両者ぶんが1ファイルに入る）
3. data/scripts.json を置き換えて push する
   → Claude Code に「台本を更新したので配信して」と頼めばよい
4. まりが次にアプリを開いた時点で反映される
```

**オフラインでも動く。** 取得に失敗しても前回の台本がIndexedDBに残っているので練習は続けられる。取りに行くのは自分のサイト内のファイルだけなので、**外部CDNを参照しない方針は維持している。**

## 7. 音声

### 7.1 抽象化

UIコードが内蔵／外部の別を意識しないこと。

```js
EST.speech = {
  async prepare(text, opts),   // 事前生成（外部のみ意味を持つ）
  async speak(text, opts),     // Promise<{durationMs}>
  cancel(), setRate(r), isAvailable(), getVoices()
}
```

`durationMs` の実測値は、カウント判定（§2.3）と S3 の目標時間に使うので**必ず返すこと**。

### 7.2 内蔵TTS（Web Speech API）

```
- voices の非同期ロード: getVoices() は初回空配列。'voiceschanged' を待ち、
  200msのリトライを3回。
- 英語ボイス自動選択: lang が en-US/en-GB/en のうち
  name に "Google"|"Samantha"|"Ava"|"Natural"|"Enhanced" を含むものを優先。
- iOS Safari: 最初の発話はユーザージェスチャの同期処理内で speak() が必要。
  起動後の最初のタップで無音の Utterance(" ") を鳴らして解錠する。
- Chrome既知バグ: 15秒以上の連続発話で停止。再生中は10秒ごとに
  pause() → resume() を呼ぶワークアラウンド。
- 画面遷移時に必ず speechSynthesis.cancel()。忘れると別画面で喋り続ける。
- end イベントが来ない場合の保険: 想定所要時間の2倍でタイムアウト。
- durationMs は start〜end の実測値を返す。
```

**話者ごとに声を変える。** `speakers[].gender`（§5.1）を見て、男女で別のボイスを割り当てる。会話台本は誰の台詞かが音で分からないと、通して再生もシャドーイング（S4）もロールプレイ（S6）も頭に入らない。**同じ声で2人ぶん喋られると、対話ではなく朗読になる。**

```
1. 英語ボイスを上の優先順で並べる
2. name や voiceURI から男女を推定し、gender ごとに1つずつ確保する
3. 片方しか取れなければ、同じボイスで pitch を ±0.15 ずらして区別する
4. それも無理なら同じ声で通す（機能は止めない）
```

ボイスの品揃えは端末で大きく違うので、**取れなかった場合は静かに劣化させる**こと。設定画面では話者ごとに手動で選び直せるようにする。

### 7.3 外部TTS（プロキシ経由・任意）

**v1では実装しない。** §7.1 のインターフェースを守っておけば後から差し替えられるので、設計だけ残して手はつけない。以下は将来足すときのための覚書。

シャドーイング（S4）の質は音声の自然さに左右されるので、いずれ外部TTSを選べるようにしたい。ただし必須ではなく、内蔵TTSでも定着ループは成立する。

**APIキーをブラウザに置かない。** 単一HTMLを配布・公開したときに漏れること、および主要TTS APIがブラウザからの直接呼び出しをCORSで許可していないことが多いこと、の2つの理由から、**Cloudflare Worker を1枚挟む**構成にする。無料枠で足りる。Workerにキーを置き、アプリにはWorkerのURLと合言葉だけを設定する。

```
[アプリ] --POST /tts {text, voice}--> [Worker] --> [TTS API]
         <--------- audio/mpeg ------
```

Worker側の要件は、CORSヘッダを返す、`Authorization` を付けて上流へ中継する、バイナリをそのまま返す、リクエスト長に上限を設ける、の4点。50行程度。雛形を `tts-proxy-worker.js` として同梱する。

### 7.4 音声キャッシュ

外部TTSは呼ぶたびに課金と待ち時間が出るので、**生成音声はBlobでIndexedDBに保存し、同一テキスト＋同一ボイスなら二度と呼ばない**。

```js
cacheKey = sha1(`${text}|${voiceId}|${model}`)   // 速度は含めない
```

トピック詳細に「音声を一括作成」ボタンを置き、全行を事前生成する。完了後はそのトピックが**完全オフラインで高品質音声のまま使える**。通勤中に使うことを考えるとこれは効く。

### 7.5 速度制御

内蔵TTSは `rate`。外部TTSは**生成時は常に speed=1.0 とし、再生時に `<audio>.playbackRate` で変える**。キャッシュが速度ごとに増えず、再生中でも速度を変えられる。`preservesPitch` は既定でtrueだが明示的に設定する（古いSafari向けに `webkitPreservesPitch` も併記）。

段階は 0.7 / 0.85 / 1.0 / 1.15 / 1.3 の5段。

## 8. ホーム画面と日々の運用

```
ホーム
├─ 🔍 検索                        ← 全トピック横断。日本語でも英語でも引ける
├─ 今日  ▸ 5日連続 / 今日 6周（約6分）
│    [ 声を出せる ]  [ 出せない ]   ← セッション開始時に1回だけ聞く
├─ 再確認  8件（文5・語3）          ← 定着から7日経過。文と語を混ぜて出す
├─ 語彙をまわす
├─ トピック一覧
│    空港でSIMカードを購入する
│    b2/4 ・ S3 見て読む ・ 定着 5/22 ・ 語彙 12/19 ・ 累計 68回
│    [続きから]  [一覧を見る]
├─ ＋ 新規トピック（貼り付け / JSON / 空から作る）
└─ 設定
```

「声を出せる」を押せば音読ステージへ、「出せない」を押せば書くドリルへ入る。**判断を1タップに畳む**のが要点で、モード選択メニューを並べると選ぶ時間が生まれて音読が始まらない。

トピックを開くと「続きから」1ボタンで即座に練習が始まる。**ステージ選択画面を挟まない。** 現在のブロックとステージから自動的に再開し、変えたい場合だけ切り替える。起動から音読開始まで2タップ以内を目標にする。

ただし**そのトピックで S0 が未完了なら、最初に語彙の下ごしらえへ回す**。知らない語を抱えたまま音読に入らせない。

「今日の目安」として `dailyGoalLaps`（既定10周）を提示し、達成したら「今日はここまでで十分です」と明示する。終わりを示すことが継続に効く。

## 9. 書くドリルと差分採点エンジン

§1.7の「書くレーン」の中身。声を出せない時間に、同じ台本を別の入り口から叩く。

### 9.1 和文英訳ドリル

和文だけを表示し、キーボードで英文を入力する。対象は自分の役の行、順序はシャッフル。音読レーンのS5の筆記版にあたる。

ヒントは3段階で、**使っても減点しない**。①語数だけ表示 `_ _ _ _ _`、②最初の1語を表示、③チャンクを並べ替え候補として提示（§1.8のチャンクをそのまま使う）。減点するとヒントを避けて詰まったまま終わるので、使わせたほうがよい。

レイテンシは測らない。打鍵速度が混ざって反射の指標にならないため、正答率と誤りの種類だけを記録する。

### 9.2 ディクテーションドリル

音声を聞いて英文を書き取る。イヤホンさえあれば電車でもできる。全文書き取りと、キーワード穴埋めの2段階。

**「3回以内で書けた率」を指標にする。** 回数無制限で聞いて正解しても実力を反映しないため、再生回数を必ず記録する。速度は0.7倍を下限とする（落としすぎると練習にならない）。

穴埋めの空欄は自動選択する。ストップワード約60語を除いた内容語のうち、①その行の `note` に出てくる語、②`words[]` に登録されている語、③文中で最も長い語、④動詞と思われる語、の順に優先し、1文あたり1〜3語。5語以下の文は1語のみ。4択にする場合のダミーは、**同じトピックの他の行から語長と品詞が近い語を借りる**（外部辞書なしで作れて、紛らわしさも適度になる）。

### 9.3 差分・採点エンジン

和文英訳とディクテーションで共用する。

**正規化**（解答・模範解答の両方に適用）

```
1. 小文字化 / 前後空白除去 / 連続空白を1つに
2. カーリークォート ’ “ ” → ' " に統一
3. 文末の . ! ? を除去、文中のカンマを除去
4. 短縮形の展開: I'm→i am, don't→do not, it's→it is, let's→let us,
   can't→cannot, won't→will not, 'll→ will, 've→ have, 'd→ would, 're→ are
   ※ it's（it is / it has）のように曖昧なものは両方を候補に持つ
5. 数字の表記ゆれ: "2" ⇔ "two"（1〜20と主要な数の辞書で吸収）
6. 単語配列に分割
```

**マッチングとスコア**

模範解答（`en`）と `alt[]` の全候補と比較し、最高スコアのものを採用する。差分は**単語単位のLCS（最長共通部分列）**で取る。編集距離ではなくLCSにするのは、「どこが余分／足りない／違う」を色分け表示するため。

```
score_base = 100 × LCS長 ÷ max(解答語数, 模範語数)
語順ペナルティ = 位置が大きくずれた語の数 × 3（上限15）
score = clamp(score_base − 語順ペナルティ, 0, 100)
```

**誤りの分類**（学習上の価値はここにある）

| タグ | 判定 | 表示 |
|---|---|---|
| `article` | 差分が a/an/the の有無のみ | 冠詞 |
| `plural` | 語幹一致で s/es の違いのみ | 単複 |
| `tense` | 不規則動詞テーブル＋ed語尾で同一動詞と判定 | 時制 |
| `preposition` | 前置詞リスト内での置換 | 前置詞 |
| `wordorder` | 語の集合は一致、順序のみ違う | 語順 |
| `missing` | 模範にあり解答にない内容語 | 抜け |
| `extra` | 解答にあり模範にない内容語 | 余分 |

`article` `plural` `tense` `preposition` のみで構成される誤りは**「惜しい」判定**とし、赤ではなく黄色で表示する。ディクテーションではさらに大文字小文字も別枠にする（聞き取れているのに落とすのは別問題）。

| strictness | 合格ライン | 惜しい系 |
|---|---|---|
| loose | 70点以上 | 合格 |
| normal | 85点以上 | 合格（警告表示） |
| strict | 完全一致 | 不合格 |

**「これも正解として登録」ボタンは必須。** 自分の答えも正しいと判断したときに押すと、入力文が `alt[]` に追記され、以後は正解になる。英語は正解が1つではないので、これが無いと英作文ドリルは必ず使われなくなる。追記結果はトピックに保存され、エクスポートにも含まれる。

**結果表示**は、模範解答と自分の解答を上下に並べ、単語ごとに色分けする（一致＝黒、抜け＝薄赤の下線、余分＝取り消し線、惜しい＝黄）。誤りタグを丸バッジで出し、`note` があれば下に添え、模範解答を再生するボタンを置く。

### 9.4 レーンをまたぐ扱い

書くレーンの結果は同じ `Progress` に書き込む。`counts.total` は加算される。ただし**定着の認定は音読レーンのレイテンシでのみ行う**（§1.4）。書くレーンで満点でも `mastered` にはしない。

逆方向の連動は入れる。**書くレーンで落とした行は、次の音読セッションで優先的に出題される。** 書いて間違えた文は、口でも出てこない。

## 10. 技術的な制約

### 10.1 `file://` で失われる機能

| 機能 | file:// | HTTPS |
|---|---|---|
| 内蔵TTS | ○ | ○ |
| IndexedDB | ○ | ○ |
| **マイク（音量検知）** | △ | ○ |
| Screen Wake Lock | × | ○ |
| Service Worker / ホーム画面追加 | × | ○ |

仕様上 `file://` はセキュアコンテキストに含まれるのでChromeデスクトップでは録音が動くことがあるが、Service Workerはオリジンがopaqueになるため動かず、スマホでローカルHTMLを開いてマイク権限を取る運用は現実的でない。

**このアプリは音量検知が中核なので、HTTPS配信を前提とする。** GitHub Pages（private repo + Pages）か Cloudflare Pages に置き、そのURLをホーム画面に追加して使う。外部TTSのWorkerを立てるならCloudflareに揃えるのが楽。

`file://` で開かれた場合は起動時に検出し、タップモードで動かしつつ「マイク自動カウントを使うにはWeb配信が必要」と1行だけ表示する。

### 10.2 iOS Safari

音声再生はユーザージェスチャ起点必須。バックグラウンドで発話が止まる。ホーム画面追加したPWAとSafariでIndexedDBが別扱いになることがあるので、初回起動時にバックアップ復元の導線を分かりやすく置く。

iOSはホーム画面未追加サイトのストレージを7日間未使用で消すポリシーがある。30日ごとに控えめなバックアップ促進バナーを出す。

マイク権限はページごとに毎回聞かれることがある。**セッション開始のたびに権限ダイアログが出ると萎える**ので、ホーム画面追加を強く推奨する案内を初回に出す。

### 10.3 電池と発熱

20ms間隔の解析ループを10分回すことになる。`AnalyserNode` 自体は軽いが、`requestAnimationFrame` で回すと画面描画と同期して無駄が出る。**音量バーの描画は60fpsではなく15fps程度に落とす**（解析は20ms、描画は66ms間隔）。バックグラウンドに回ったら解析を止める。

### 10.4 配置とポータルへの登録

GitHub Pages に置き、既存の `nyuta-portal` の**タモやんApps**から開けるようにする。

```
リポジトリ   Tamoyan-English
公開URL      https://silmotoki-tech.github.io/Tamoyan-English/
公開設定     main ブランチのルート（GitHub Pages の既定）
公開される   index.html（build.js の出力）と data/scripts.json
ポータル側   tools-config.js に1件追加（アプリ本体には手を入れない）
```

まりには**ポータルのURLだけを渡し、ホーム画面に追加してもらう。** アプリのURLを直接渡さないのは、今後アプリが増えたときに入り口を1つに保つため。

**台本の更新とアプリ本体の更新は別問題である。**

台本は `data/scripts.json` を `?t=` 付きで取りに行くので確実に届く（§6.5）。**しかしアプリ本体（`index.html`）にはその仕組みが無い。** GitHub Pages は `max-age=600` を返すうえ、iOSのホーム画面追加アプリは古い `index.html` を10分どころではなく長く抱え込むことがある。

自分だけで使っているうちは強制リロードで済むが、**まりが使い始めたあとは「直したはずのバグが相手の端末で直っていない」という形で出る。** 本人に強制リロードの手順を説明することになり、原因も分かりにくい。

対策は**まりに渡す前**に入れる。ネットワーク優先のService Workerを置いて、新しい `index.html` があれば取りに行き、無ければキャッシュで動かす形にする（`nyuta-portal` で既に使っている方式に揃える）。F5でポータルに出す前に必ず片付けること。

## 11. 実装フェーズ

優先は **読み上げ・シャドーイング（F5）** と **ロールプレイ（F7）**。この2つに最短で到達する順序に並べてある。各フェーズの終わりで必ず動く状態にすること。

**F1 土台** — IndexedDB、スキーマ検証、**テキスト貼り付けからの解析**、JSON入出力、編集プレビュー、ブロック自動分割、チャンク自動分割、全体バックアップ、ハッシュルーティング、ホーム、トピック一覧。サンプルトピックを2つ内蔵し（空港チェックイン12行／SIMカード22行）、短い台本と長い台本の両方を確認できるようにする。

加えて**プロフィール選択（§5.9）と配信JSONの取得（§6.5）**をF1に含める。プロフィールは進捗キーの設計そのものに関わるので、後から足すと全ストアの作り直しになる。F1時点では進捗を書き込む画面がまだ無いので、**キーの設計と選択UI・読み取り専用モードの切り替えまで**を入れる。

**F2 一覧モードと検索** — 和訳の箇条書き＋タップで開く一覧、和英の反転、横断検索、テキスト書き出し。**軽いわりに毎日使うので早い段階で作る。** 開いた行を復習キューに入れる連動もここで入れる。

**F3 内蔵TTS** — 音声エンジン抽象化と内蔵実装。`durationMs` の実測を含む。**外部TTSは実装しないが、差し替えられる形にしておく。** この時点で「台本を入れて聞き流す」ができる。

**F4 音量検知エンジン** — 較正、発話検知、カウント判定、レイテンシ測定、詰まり検知と位置推定、音量バー。**UIから独立した単体モジュールとして作り、コンソールから `EST.mic.start()` で動作確認できる形にする。** ここがバグると全部が崩れるので、先に単体で完成させる。

**F5 ステージS1〜S4（読み上げ・シャドーイング）** ★最優先 — 練習画面、ステージ進行、進級条件、積算メーター、目標時間バー、Screen Wake Lock、タップモードのフォールバック、ブロック単位の進行。**ここまでで「毎日音読する」が成立する。**

**カウント成否の判定（§2.3）はここで実装する。** `EST.mic` の `rep` が返す `spokenMs` と、`EST.speech` が返す `expectedMs` を突き合わせる。あわせて **`countRatio` を設定画面から変更できるようにする**（§2.3）。F4では判定そのものが無いため設定項目も置かない。ここで拾い直すこと。

**F6 語彙（S0と語彙モード）** — 語彙の自動抽出、S0の下ごしらえ、語彙復習モード、長押しで語を拾う、Anki用TSV書き出し。判定ロジックはF4・F5のものを共通関数として使い回す。

**F7 ステージS5〜S6（ロールプレイ）と積み上げドリル** ★最優先 — シャッフル、和訳キュー、相手の台詞に返すモード、役交代、定着判定、7日後の再確認（文と語の混合キュー）、全ブロック完了後の通しモード、後ろから積み上げるドリル。

**F8 可視化** — レイテンシ推移グラフ、定着行数、ストリーク、日次ログ、よく詰まるチャンクの集計。

**F9 書くレーン** — 差分採点エンジン、和文英訳ドリル、ディクテーションドリル、穴埋め、「これも正解として登録」、レーン間の連動。**声を出せない時間の受け皿なので、音読レーンが回り始めてから作る。**

**F10（v1対象外）外部TTS** — Cloudflare Worker、プロキシ接続、音声キャッシュ、一括事前生成、playbackRate制御。内蔵TTSで不満が出てから着手する。

**F5まででアプリとして成立する。** F7でようやく「反射」が測れるようになり、ここが本来の目的地になる。F2の一覧・検索をF5より前に置いてあるのは、実装が軽いわりに毎日開く画面になるためで、先に手元にあると設計の手触りを早く確認できる。

## 12. 実装時に守ること（Claude Code向け）

**音量検知（`mic.js`）は必ずUIから独立させる。** イベントを発火するだけのモジュールにし、UIはそれを購読する。UIに埋め込むとデバッグが不可能になる。

```js
EST.mic.on('onset',  ({t}) => ...)
EST.mic.on('offset', ({t, durationMs}) => ...)
EST.mic.on('level',  ({rms}) => ...)      // 音量バー用
EST.mic.calibrate()   // Promise<{noiseFloor, onsetThreshold}>
```

**閾値と係数はすべてファイル先頭の定数にまとめる。** `ONSET_MULTIPLIER`, `COUNT_RATIO`, `MASTERY_BASE_MS`, `MASTERY_PER_WORD_MS`, `STALL_MS`, `S3_TIME_FACTORS` など。実機で必ず調整することになる。

外部CDNを参照しない。全部インライン。`localStorage` ではなくIndexedDBを使う（設定のミラーのみ可）。グローバル変数を作らず `window.EST` 名前空間の下にぶら下げる（1ファイル結合のためESモジュールは使わない）。

**エラーを握りつぶさないが、ユーザーに見せるものとコンソールだけのものを分ける。** マイクやTTSの失敗は「使えない環境である」ことがほとんどなので、ダイアログではなく機能の非表示か静かなフォールバックで対処する。

UIラベル・ボタン・エラーは日本語。コメントも日本語で、特に「なぜそうしたか」を残す。英文は `-apple-system, "Segoe UI", Roboto`、日本語は `"Hiragino Sans", "Noto Sans JP"` とフォントを分ける。英文が日本語フォントで表示されると読みにくく、音読の質に響く。

開発は `src/` に分割して書き、依存ゼロのNodeスクリプトで**リポジトリ直下の `index.html`** に結合する。

```
src/js/  00-store.js  01-schema.js  02-speech.js  03-mic.js  04-stage.js
         05-mastery.js  10-ui-home.js  11-ui-practice.js  12-ui-import.js
         13-ui-settings.js  99-main.js
```

**出力先を直下の `index.html` にするのは GitHub Pages の制約による。** Pages が公開できるのはリポジトリ直下か `/docs` だけで、`dist/` は公開できない。既存の他アプリ（nyuta-portal、麻酔量計算、手術見積）もすべて直下公開の形になっているので、それに揃える。

```
Tamoyan-English/
├── index.html          ← build.js の出力。これが公開される本体
├── data/scripts.json   ← 配信台本。build.js は絶対に触らない
├── build.js
├── src/                ← 開発用の分割ソース
├── docs/SPEC.md
└── CLAUDE.md
```

**`build.js` が生成するのは `index.html` だけ。`data/scripts.json` には一切書き込まない。** ここはタモやんが配信のたびに更新する運用データで、ビルドで上書きすると公開中の台本が消える。サンプル台本2本は `index.html` 側に埋め込み（初回起動と オフライン時の土台）、`data/scripts.json` は配信チャンネルとして独立させる。
